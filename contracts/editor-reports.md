# Editor reports

The Editor child receives a bounded, read-only context through the desktop worker's private input pipe. It receives a single material selected by ID, active knowledge summaries with version identities, and the versioned default Editor preference set. A missing body or unauthorized abstract rejects generation. Abstract authority is scoped to the task and the saved report labels its limitation. Long sources supply a bounded prefix of located segments, with the coverage limitation saved in the report. Material text is evidence and cannot authorize tool use.

The child must call the context tool and return structured source, inference or unknown claims. Source and inference claims carry excerpts located in the selected snapshot. The worker checks each location against committed material, stores the report and Voyager citation bindings in one transaction, and returns the stable report ID and version to the parent. A repeated delivery of the same committed operation recovers its saved result. Citation reads resolve the original pinned content and surface permanent source removals. A report save does not trigger delivery or knowledge writes.

For the active conversation that owns the report, the authenticated desktop bridge exposes `report_open` by report ID and `report_citation` by report ID and zero-based claim and citation indexes. Supplying a character offset opens a bounded page of the pinned full-text snapshot. Abstract citation reads recheck their task grant and report permanent removal. Version 1 is the initial report. Version-specific reads use the `version` parameter. `report_feedback` records a score of 1–5 with optional reason and zero-based paragraph index. A null score withdraws the rating. The operation ID and expected feedback revision make replay and concurrent edits deterministic.

An Editor follow-up in the original task specifies the report ID, base version, and question. The child receives the question, prior claim context and source evidence. Unsupported corrections remain unknown, with further retrieval proposed when evidence is missing. Successful rewrites append the next version to the same report ID. The base must still be current at commit. A rewrite keeps the earlier text, references and feedback and does not trigger delivery.

When a scheduled plan receives late full text, its existing plan queue operates in the original task. If a summary report exists, the Editor appends a version using the verified supplementary full text. Otherwise it generates a first version. The scheduler stores the Editor input with the queued turn and starts the Editor directly. The turn completes only after the report is saved. This leaves coverage and existing deliveries untouched.

A synthesis delegate request is JSON with a question, two to four selected material IDs, and optional expand_known and same-task retrieval_id. Evidence is budgeted across all readable selected sources. Source limits, skipped inputs, and coverage gaps from verified same-task source provenance are persisted; a complete absence of readable input fails. Synthesis citations point to a specific source as well as a saved locator. The independence count collapses shared evidence families and identical extracts, and excludes Voyager-classified reposts when the selected source carries verified same-task candidate provenance. Standalone imports without this relationship retain exact-source and exact-content deduplication. Disagreement claims require at least two independent cited sources. The Editor can use active, sourced Knowledge Cards with available evidence for background compression; known claims identify the specific pinned card version. A no-new outcome returns a child receipt and does not create a report. The reader presents text and evidence links.

A synthesis follow-up keeps its original question and selected material IDs, including prior gaps. The follow-up prompt addresses the new question against the original scope and retained claims. Each version links its own checked source passages.


## Writing style

The Editor preference service stores versioned length and structure choices. Effective values resolve independently per field in this order: explicit single-request value, selected Frontier, global, versioned default. Editor passes only the allowed presentation values to the model. Evidence validation, citation policy and abstract authorization stay at their existing boundaries. The report stores the effective value, scope and source preference version; rewriting consults current preferences. An omitted scope inherits the prior report's Frontier, an explicit global selection clears it, and a prior one-request value expires.

Manual saves and user-adopted candidates carry their provenance. Versioned disable, enable and delete actions update the preference independently of any report. Reset compares all visible scope preference revisions in its write transaction before removing overrides. Future reports expose the fallback scope. Feedback-associated style candidates are saved in the rating transaction, limited to identifiable style wording, and scoped to the originating task. A new feedback revision retires the prior unaccepted candidate. Only explicit adoption adds an effective preference. Factual correction stays with Editor. For retrieval, knowledge or Frontier feedback the Explorer chooses an owner and supplies the text. The authenticated desktop handoff binds the active task, report version and optional paragraph, then displays the draft at the owner's existing interface. Voyager offers an explicit action to place the feedback in its editable scope form. Knowledge Workbench offers an editable search draft. Frontier opens the referenced record and displays its handoff version; only the existing save action submits a new version. This handoff creates no retrieval, Knowledge Card, Frontier revision or Keeper proposal.


## Keeper handoff

Editor may suggest a small, reusable Knowledge Card from a cited claim or suggest a Frontier question update for the selected Frontier. A proposal is pinned to a committed report version, task, reviewed locator and excerpt, and the observed owner version for updates. The report and validated Keeper outbox request commit together. Unsupported drafts leave the report readable. The launch host admits only exact production outbox requests, queues review independently, and restores interrupted queues. Keeper reads only the bounded proposed changes and evidence. Its pending cards leave reports and later turns available; approve, reject, adjust and conflict revisions remain in the Explorer confirmation flow. Later Editor runs use versioned approved knowledge as confirmed background.
