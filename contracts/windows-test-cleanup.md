# Windows test-instance cleanup primitives

The internal target-schema runner calls the installed package's explicit `AgentService.initialize_database(db)` entry; ordinary construction uses the same method. Before loading target bytes it checks manifest/module FileIDs, the caller's verified manifest digest and the module digest. Compilation of verified bytes avoids unregistered bytecode files. The tool's compatible runtime executes this current pure-SQL/stdlib entry; this does not verify the target runtime or all its dependencies. Target module top-level code is trusted package code, not sandboxed SQL. A completed snapshot containing the original database is required before any schema mutation. Missing interfaces or database-less snapshots are refused. SQL failure is handled by coordinated code/data/version restoration; failed restoration retains the overall pending marker. Public managed upgrade supports this compatible schema interface for initialized, enrolled instances; a database-less instance remains blocked.

Internal code transactions seal before/after FileIDs and original-content digests. `rollback_code_transaction` restores original files by handle rename and retains new files under the enrolled transaction's `failed` directory. It validates all current/backup identities and original bytes before rollback writes, holds all ancestors throughout, and rejects foreign replacements. Source/destination alias receipts bracket each rename; failure or process interruption leaves the pending marker, and retry resumes from observed enrolled identities. Repeated rollback is supported. The public coordinator combines this primitive with data and version restoration.

Upgrade data snapshots cover registered `horizon.sqlite3`, `agent/model.json`, `version.json` and fixed Pi session files. They do not scan or adopt other data. Each file under `data/upgrade-backups/<snapshot-id>` is atomically created and identity-enrolled before writing; completion and content digests are sealed separately. SQLite uses its backup API with the existing PERSIST source contract; WAL-format sources and unknown sidecars are refused before SQLite access. Restore verifies snapshot identities/digests and existing target identities before writes, rejects an unfinished model transaction, and holds an upgrade marker during in-place restoration. A partial write leaves startup blocked until retry succeeds. Foreign replacements are retained. The snapshot primitive alone does not remove files/sessions created after its snapshot. The upgrade coordinator excludes concurrent application writes and supports the verified target pure-SQL schema entry; unknown pre-existing content remains untouched, not retroactively enrolled.

Restoring intentionally replaces the current contents of still-enrolled targets, including legitimate application changes made after the snapshot. It does not accept changed snapshot bytes: a backup digest mismatch or a replacement FileID at either endpoint blocks restoration.

`managed_upgrade.stage_code_transaction` is the internal code-publication primitive used by public managed upgrade. It validates a local package, enrolls every new file before content writes and moves existing enrolled files to per-operation backups through original handles. Both source and destination names are recorded in the DPAPI-protected registration around a rename so interruption does not discard known FileIDs. A pending marker blocks application use; startup rechecks it after acquiring the shared lease while holding the entrance gate. Full cleanup can remove enrolled transaction content, and initialization clears the marker only after all controlled children are absent. An unregistered directory left by a failed receipt is preserved.

Managed renderer launches discard raw stderr and remove inherited `ELECTRON_LOG_FILE` / `ELECTRON_ENABLE_LOGGING` overrides instead of creating `data/desktop-electron.log`. Existing unregistered logs are not adopted or removed. Diagnostics retain fixed `renderer_start_failed` and `renderer_exit` categories with the observed process exit code; they do not retain stderr text. Ordinary desktop launches keep their original raw-log behavior. Shared immutable Electron runtime caches remain outside instance cleanup ownership.

After a validated managed desktop startup fails, the real module entry shows a fixed exception category and attempts a retained sanitized report. It does not write an unregistered `desktop-error.log` or emit the original traceback. A report-export failure remains visible and directs the user to the independent report command. A generated report path means an artifact exists, not that every snapshot item was available; inspect its availability fields. Invalid/busy instances still refuse without diagnostic-home writes. Ordinary desktop failures retain their previous traceback behavior.

The development tool builder `scripts/prepare_cleanup_tool.py --inputs <offline-inputs> --output <new-directory>` verifies the fixed CPython 3.13.7 amd64 and PyYAML 6.0.2 inputs in `installer/cleanup-runtime-inputs.json`, reuses the runtime assembler and copies an explicit tool-module list. It never copies the developer interpreter or installed application. `cleanup-tool.cmd` runs its adjacent isolated runtime; the input and per-file manifests provide build verification, not runtime tamper resistance. Existing output directories are refused. This artifact is not the final Windows test kit.

For human use, append `--interactive` to `cleanup`: it prints scope before reading the complete instance ID, and EOF or any other answer cancels without report creation or deletion. `--confirm` remains mutually exclusive automation authorization. No command reports complete P5 acceptance.

`python -m hostrun.cleanup_cli` exposes `prepare`, `install <id> --package <zip> --sha256 <digest>`, `preview <id>`, `report <id> --output <directory>`, `recover <id> --sha256 <pending-artifact-digest>`, and `cleanup <id> --output <directory> [--mode full|keep-data] [--confirm <id>]`. It uses the fixed control root and rejects overlap with its own code/runtime. Preparation creates a fresh initialized instance; it cannot adopt a path. Preview lists registered file candidates and empty-directory candidates: deletion still revalidates identities and preserves unknown content. Cleanup without confirmation only previews. The low-level automation flag accepts the exact instance ID and prints the plan before executing; a future human-facing kit must display the plan and then request confirmation. JSON results always carry `scope_complete: false`; blocked, partial and incomplete outcomes exit 2. Reports pin all output ancestors and atomically create/hold the final directory through `instance.json` and `cleanup.json`. Recovery is an explicit user operation: ordinary upgrade returns `managed_upgrade_recovery_pending` and never automatically recovers or resubmits the upgrade. The pinned independent runtime and interactive confirmation entry are available; final kit wiring and complete P5 acceptance remain pending.

GUI report exports for managed instances default to `%LOCALAPPDATA%/Horizon/test-reports/<instance-id>/`, a retained sibling outside `test-instances`. Parents stay pinned and reject reparse points; the unique final directory is atomically created and held until all report files are written. Cleanup leaves these reports intact. Old unregistered `data/diagnostics/reports` contents are preserved with a partial cleanup result. Ordinary-home defaults and explicit export destinations retain their existing behavior.

DesktopWorker transmits initial conversation history as one `history` frame on the existing Node stdin pipe, with no `agent/history` temporary file or directory. The same line reader continues handling delegation replies. Pi imports history only when the persistent session has no entries; retries consume but do not re-import the frame. EOF marks the owner disconnected and rejects later delegation instead of leaving an unresolved request. Stopping the worker terminates the child and releases a blocked large history write. The external `--history-file` entry remains compatible; pre-existing unregistered history files are preserved, not retroactively adopted.

Managed desktop locking and activation use the fixed enrolled `desktop.lock` and `desktop.activate` files. The existing advisory desktop lock still selects the owner; a second real desktop entry emits a coalesced one-shot signal and exits. Consumption deletes only the opened, identity-verified signal. A later signal atomically creates and enrolls a new identity, and cleanup handles either a pending signal or an already-consumed one. Foreign lock/signal replacements are preserved. An invalid controlled activation identity fails closed: the desktop main loop exits rather than repairing or adopting the file. Missing managed layout refuses startup instead of creating an unregistered home.

Managed AgentService connections atomically create and enroll `horizon.sqlite3` and its fixed `-journal` before SQLite opens them, then hold original file/ancestor handles for the connection. An external database lock serializes managed connections. Before schema access, SQLite uses exclusive locking and PERSIST journaling so hot-journal recovery and commits keep the enrolled journal identity; ordinary homes retain their previous SQLite behavior. Unknown WAL/SHM files or a WAL-format database are rejected, not adopted or migrated. Transaction failure closes the connection and releases handles; process interruption before/after commit recovers through SQLite. The independent read-only diagnostic snapshot waits at most 250 ms for a busy database and stops querying after an SQLite error. An unavailable snapshot of an enrolled database marks the report incomplete and blocks cleanup before process stopping/deletion. Managed upgrades use the enrolled snapshot path instead of the legacy backup implementation.

Managed diagnostics enroll the directory and the two fixed `events.jsonl` / `events.previous.jsonl` files before appending. Writers try the inventory lock without waiting and skip an event while it is busy; held handles verify each identity. Rotation preserves both FileIDs: the previous segment is flushed before clearing the current segment. An interrupted rotation may duplicate events; this is bounded best-effort diagnostics, not lossless history. It does not infer ownership from filenames or re-scan contents. Unknown replacements refuse further writes and remain preserved by cleanup. Registration failure removes the still-empty newly created entry; diagnostics do not block recovery. Managed exports live in retained report directories outside the removable instance; old unregistered internal reports remain preserved.

Managed Pi uses the public in-memory credential store; the enrolled model configuration remains the sole credential file. Persistent sessions use the SDK's public header and `SessionManager.open` on a fixed `session.jsonl`. Before any session content is written, a short-lived Python pipe guardian atomically creates and registers the directory/file identities, then holds ancestor/file handles and a shared lifecycle lease for the Node session. It inherits existing Job containment and exits on stdin EOF, including Node termination; normal shutdown waits for release with a five-second kill fallback. Unexpected guardian loss terminates Node. Empty/truncated initial headers stay blocked without SDK-generated identity drift and remain safely cleanable. Foreign replacements and unknown neighbor files are retained. Existing unregistered Pi files are never adopted by scanning.

Managed model configuration enrolls `data/agent/model.json` and its parent directory. CLI configuration and GUI discovery/selection/refresh use the same writer. Updates write a new enrolled temporary file before publishing; a DPAPI journal records old/new FileIDs and temporary/backup paths. Old-to-backup and new-to-target handle renames are a recoverable multi-step transaction, not an atomic filesystem replacement. The backup remains until the new identity is committed. Python readers and the bundled Node reader use the same inventory lock and recover the journal before reading. Node receives credentials through a private Python stdout pipe, never arguments or environment variables; reader failures expose fixed categories only. Recovery accepts only enrolled identities and preserves foreign replacements. GUI read-modify-save compares both expected FileID and contents under the write lock, rejecting stale results. Full cleanup removes enrolled configuration and temporary/backup residues; reinitialization clears previous inventories.

Test instances use `%LOCALAPPDATA%/Horizon/test-instances/<instance-id>` with separate `app`, `data` and `archive` children. Existing installations are not adopted. Registration and lifecycle locks live outside these removable children. Ordinary data homes outside this controlled root retain their existing lifecycle.

Current-user Windows DPAPI protects registration integrity and binds it to the registration path. The record contains volume/file identities for the instance and enrolled children. Missing, altered or replaced identities refuse startup before writing the data home. This protects against corrupted or substituted records; it does not claim protection from a malicious process with the same user's DPAPI authority.

Desktop holds a shared lifecycle lease; managed upgrade and cleanup require exclusive leases. The existing desktop lock still controls window activation. Lease and identity failures exit without creating diagnostic files in the blocked home.

Managed desktop owners publish an external DPAPI-protected process record only after establishing the Horizon Job and taking the desktop lock. It contains PID, Windows creation time and `image_path_digest` (a hash of the normalized executable path, not of executable bytes). After diagnostic export succeeds, cleanup holds the instance entrance gate, opens and verifies that exact owner process, and terminates only that handle. The existing non-inheritable, owner-only `KILL_ON_JOB_CLOSE` Job supplies descendant containment. Cleanup waits up to five seconds for the owner and the process handles captured in a parent/child snapshot; `observed_processes` counts that snapshot, not an enumeration of every Job member. Identity mismatch, inaccessible processes or timeout block deletion. The entrance gate prevents a new desktop, upgrade or test installation from starting between stopping the owner and taking the exclusive lifecycle lease.

Initialization requires Windows 10 or later. `NtCreateFile` uses `FILE_CREATE` and a single-component name relative to a held parent directory handle. Newly created staging directories and children remain held through enrollment. A protected journal precedes child moves through handle-based rename. Recovery verifies enrolled identities; unknown staging residues are retained and identified by hashes in independent reports.

Cleanup requires explicit instance-ID confirmation and successful independent allowlisted diagnostic export outside the controlled root. Deletion pins ancestors, rejects reparse targets and uses `SetFileInformationByHandle(FileDispositionInfo)` on the opened target. It never recursively deletes an arbitrary recorded path. Completed deletions remain reported if a later item fails. Unknown content is preserved and prevents a clean result.

Deletion requires a committed file-identity inventory. Historical root names (`model-config.json`, `horizon.sqlite3`, its WAL/SHM files and `version.json`) do not prove ownership: an entry without a matching enrolled identity remains preserved and yields `partial`. The first-install package entry installs into the enrolled `app/current` container and seals verified manifest files, known installer metadata and parent-directory identities. Cleanup checks those identities through held handles, removes registered files and then registered empty directories. Unknown contents remain. Keep-data mode preserves data/archive and reports `uninstalled` only when no unexpected application residue remains. Full mode reports `cleaned` only when the removable instance contents are absent; registration and the external lock remain for diagnosis and reuse.

An initial journal-write exception removes the still-empty current directory through its original creation handle. Any interrupted installation with no committed file-identity inventory returns `blocked/interrupted_inventory_unavailable`, including an otherwise complete package whose inventory commit failed. It never infers file ownership from equal content, a manifest path or a matching package digest. A process killed between creation and first journal commit can leave unregistered content; it is retained rather than adopted. Another fresh instance can be allocated safely.

This is not a completed P5 acceptance kit. Complete interrupted-first-install inventory recovery, Chromium cache ownership and full distribution/live acceptance remain outstanding. Remaining acceptance is tracked in GitHub issue #230 and `docs/acceptance/README.md`.

The managed upgrade coordinator holds one entrance gate and exclusive lifecycle lease across enrolled data backup, code publication, verified target schema initialization and version publication. Private nesting is bound to the same home, process and thread; ordinary startup has no bypass. A separate DPAPI-protected overall operation marker survives successful substeps and blocks startup until the complete sequence commits. Version contents come from the verified target manifest; newly created version files are enrolled before writes, and old versions remain enrolled backups. Code-staging exceptions or refusals, target-initializer refusals, and schema-execution/version-publication exceptions restore the registered original version identity (or original absence), original code identities and enrolled data snapshot before clearing the overall marker. The version journal is durable before moves, and missing pre-publication aliases are removed so a new attempt can proceed. Failed recovery leaves startup blocked. The explicit restart-recovery entry validates the home-bound protected operation and expected artifact digest, then restores from its complete enrolled snapshot. Before publication, an absent/incomplete snapshot is released only when there is no code transaction, local upgrade marker or version journal and registered source/partial-backup identities still match; partial backups are retained rather than copied over data. This result means identity validation permitted reopening an unpublished operation, not that SQLite consistency has already been verified: a later controlled SQLite open performs any required journal recovery. Foreign replacements or recovery failures retain the overall marker. The public service rejects either a running interpreter or its loaded upgrader module inside the target code. Artifact manifest OS/architecture/Python requirements must match the tool before any operation begins. These checks do not replace target runtime or complete desktop-package live acceptance. Managed package installation passes an extended-length IO root into the distribution installer while returning canonical code paths. Snapshot/restore and cleanup filesystem IO use extended-length Windows paths while registrations and ownership comparisons retain canonical paths. Native handles still reject reparse points and pin ancestors. Managed code validation, staging, publication and original-identity rollback also use extended IO paths without changing canonical inventory names. Focused deep-file upgrade and rollback are covered; complete distribution/schema/runtime paths still require full-chain verification.
