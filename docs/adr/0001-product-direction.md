# Horizon 产品定位与交互决策

状态：已确认。日期：2026-11-07。依据：探索者在本次产品讨论中确认的四部分闭环。

Horizon（地平线）是面向各行各业持续学习者的资料获取、知识管理与个性化解读助手。科研人员是探索者群之一，论文是资料来源之一。本决策取代此前以科研对话、论文报道、飞书知识库或飞书专属反馈界面为中心的产品定位。

## 四个组成部分

1. **资料获取**：围绕探索者关注的主题检索论文、新闻、推送、博客等网络原始资料，保留可追溯的来源，供解读与知识构建使用。
2. **知识库管理与构建**：由 Horizon 自建知识管理套件承接飞书多维表格的能力。知识卡片、命题及关联资料支持 Agent 自动新增和修改，也支持探索者手动维护。知识库代表探索者已掌握的知识；收藏资料不能直接等同于掌握知识。
3. **个性化解读撰写**：读取新资料、探索者已有知识与使用过程中积累的偏好，解释新增内容、与已有知识的关系及其变化，让探索者尽快理解并吸收。写作是独立能力，不与投递渠道绑定。
4. **定时推送 Agent**：按探索者设定自动执行检索、读取知识和偏好、撰写与投递，承接后续反馈，并形成持续学习闭环。

## GUI 与渠道

Horizon GUI 提供资料管理、知识库维护、推送阅读、评分与谈判交互，以及自动任务和偏好设置。主功能入口围绕推送收件箱、资料、知识库和自动任务组织；对话用于追问解读、纠正理解及协商知识更新。执行轨迹与 Console 是辅助工具，不再主导产品结构。

评分表达阅读体验和价值判断；谈判支持进一步表达偏好、纠正理解、讨论和调整知识更新，不能缩减为点赞或一次确认。

飞书是可选的外接前端交互与投递渠道。Horizon 自身必须提供完整闭环，核心知识库与交互不以飞书账号、多维表格或消息卡片为必要前提。

## 实现边界

这是产品决策，不是功能已完成的声明。本次仅整理文档，不修改程序。既有技术文档中的论文字段、飞书表结构、队列、校验、同步与命令保留为现有实现参考，不构成新的产品限制。不得把旧链路的逐条采纳、单篇格式、串行反馈或控制台入口推广为所有未来场景的强制交互。

自建存储的具体技术选型、迁移方案、自动更新与谈判的具体规则，须在后续实现设计中确定；本决策不自行指定数据库、审批机制或页面细节。

## 统一术语

2026-11-07 确认：软件为 Horizon（地平线），软件使用者为 Explorer（探索者）；Knowledge Base（知识库）包含 Knowledge Card（知识卡片）与 Theme（命题）。Theme 取代此前命题的英文名称 Proposition；原先用于初始构建的临时主题分组称为 Initial-build group（初始构建分组）。现有字段与接口的兼容映射见 [术语表](../../GLOSSARY.md)。

## 后续存储决策（2026-11-08）

已确认的 [Spec A](https://github.com/Moke110/horizon/issues/120) 将新产品数据放在独立于安装位置的稳定 home，使用单 SQLite 数据库，各模块经公开 command/query/event 访问所属数据。Agent 拥有任务；业务结果、操作回执与事件在同一事务提交，重复操作返回已提交结果。新建空库不导入历史工作区，通用文件工具不能写业务数据库、快照及凭据。此决定补充上文当时尚未确定的存储选型；接口契约见 [Agent application service](../../contracts/agent-service.md)。
